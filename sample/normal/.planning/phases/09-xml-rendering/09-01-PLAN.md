# Plan 09-01: Structural Tags as a Nested Heading Outline

## Goal

The robot project writes its `.planning/` documents with bare structural
tags, the same way every other phase in this workspace does, and wants those
tags readable as normal prose instead of stray angle brackets when someone
opens a plan in the status viewer. This document is that plan for Phase 9 —
and it doubles as a live fixture for the status viewer's XML preprocessing
rules: bare structural tags becoming a nested heading outline, HTML/XML
comments vanishing without a trace, and simple same-line tag pairs becoming
an emphasized tag-name label followed by the plain value. It is arranged
below to hit every rule of all three passes rather than to describe robot
work.

## Background

Earlier phases already taught the fleet to navigate, brew, and hand over a
cup. Phase 9 does not add a new robot capability; it exists so this
document's own tagged appendix can be rendered by the viewer and checked by
eye against what the three preprocessing passes are supposed to do. If you
came looking for coffee logic, it is not in the appendix below — only the
tag shapes, comments, and inline pairs are.

## Tasks

1. [ ] Confirm every opening tag in the appendix renders as a heading at the
   level its nesting depth predicts
2. [ ] Confirm attributes on a tag never reach the rendered heading text
3. [ ] Confirm the self-closing tag produces a heading without deepening the
   stack for the tag that follows it
4. [ ] Confirm the heading level caps at six even though the appendix nests
   eight tags deep
5. [ ] Confirm the fenced `xml` block stays literal, angle brackets, comment,
   and inline pair all included
6. [ ] Confirm a comment disappears completely — delimiters and body —
   whether it sits alone on a line, spans several lines, or trails a
   sentence, with no doubled blank line or lost paragraph break left behind
7. [ ] Confirm a simple same-line tag pair renders as its tag name in
   emphasis, then a colon, then the plain value, for any tag name, with
   attributes discarded, while an empty pair and a mismatched pair both stay
   literal
8. [ ] Confirm several pairs on one line are all replaced, that a value is
   trimmed before it follows the colon, and that a close tag differing from
   its opening tag only in letter case stays literal
9. [ ] Confirm the tag name in an inline pair is reproduced exactly as
   written, never title-cased or reshaped into spaced, capitalized words the
   way the whole-line heading conversion in Sections A and B reshapes a name

## GSD-style tagged appendix

Some GSD plans (this project's own `.planning/` format) use bare structural
tags instead of markdown headings. The appendix in `02-02-PLAN.md` proves
those bare tags survive instead of vanishing; this one goes further and
exercises every rule of the conversion that turns them into an outline.

### Section A — depth, attribute stripping, casing, and a self-closing tag

This block proves four things at once: an opening tag becomes a heading at
`stack_depth + 1`, an underscore-separated name becomes spaced Title Case
words, a tag's attributes never reach the rendered heading text, and a
self-closing tag emits a heading without pushing — so the tag after it stays
a sibling, not a child.

<objective>
At depth zero this line alone should become a single top-level heading,
`# Objective`, and the depth stack should now read one deep.
</objective>

<execution_context>
This tag's snake_case name should render as two Title Case words,
"Execution Context", proving underscores are separators and not literal
characters that survive into the heading text.

<task type="auto">
This heading should read as a bare "Task" with no trace of the
`type="auto"` attribute anywhere in it — attributes are discarded before the
name ever reaches the heading.
</task>

<blocked/>

<task type="checkpoint">
This heading should also read as a bare "Task", at the same depth as the
task above it, proving the self-closing `<blocked/>` tag did not push and
did not deepen the stack for anything that follows it.
</task>

</execution_context>

### Section B — the six-level cap

This block nests seven layers under a top-level `verification` tag. The
heading level should step down by one for each layer through level six, and
then visibly stop getting smaller — level six is as deep as a heading can
go, so the seventh and eighth layers both render at that same capped level.

<verification>

<layer-one>
Depth one. Kebab-case name, so this should render as two Title Case words,
"Layer One".

<layer.two>
Depth two. A period is also a name separator, so this should render as
"Layer Two".

<layer_three>
Depth three, rendering as "Layer Three".

<layer-four>
Depth four, rendering as "Layer Four".

<layer_five>
Depth five, rendering as "Layer Five" — the deepest heading level that is
not yet capped.

<layer-six>
Depth six. Uncapped this would be a seventh heading level, which does not
exist, so this should render at the same capped level as the one above it.

<layer_seven>
Depth seven, still capped at the same level as the two tags above it —
proof the cap holds even nesting deeper still.

Every layer above closes here, in reverse order, so the depth stack unwinds
cleanly and nothing after this appendix inherits a stale depth.

### Section C — the fenced contrast

The block below repeats a small slice of Section A's shapes inside a fenced
`xml` code block, plus one comment and one same-line inline pair. This is the
contrast case: all three preprocessing rules — heading conversion, comment
removal, and inline-pair emphasis — stop at a fence, because none of them
ever looks inside one. Nothing in the block below is touched: no heading
appears, no comment vanishes, and no inline pair turns into emphasis —
everything stays exactly as written, angle brackets and all.

```xml
<objective>
This line sits inside a fence, so it stays exactly as written.
</objective>
<task type="auto">
So does this one — no heading, no stripped attribute, just literal text.
</task>
<!-- this comment should also survive here, delimiters and body alike -->
Owner is <owner>Ed</owner>, but inside a fence this pair stays literal too.
```

### Section D — comments vanish without a trace

Every word in this section that explains what to look for lives in ordinary
prose, never inside a comment — the comments are the very thing this rule
makes disappear, so nothing inside one can carry an instruction to the
reader.

Paragraph one sits above a comment that occupies its own line.

<!-- a single-line reviewer note that must not render at all -->

Paragraph two follows immediately below, separated from paragraph one by
exactly one blank line — proving a comment-only line vanishes without
doubling the gap around it or closing it up entirely.

<!--
This comment spans three source lines: this opening line, this middle
line, and the closing line below it. All of it should vanish — opening
delimiter, every word in between, and the closing delimiter — leaving no
trace and no extra blank line where it used to sit.
-->

Paragraph three demonstrates the last shape: a comment trailing this very
sentence of prose. <!-- trailing note that should not render -->
The prose above survives with no trailing whitespace left behind where the
comment used to sit.

When this section renders correctly you see three plain paragraphs and
nothing else — no comment delimiters, no reviewer-note text, and no gap
wider than the single blank line that already separates every paragraph
above.

### Section E — same-line tag pairs become an emphasized name label plus the plain value

<owner>Ed</owner>

The line above is the sole content of its line: a bare same-line pair should
render as an italic `owner:` followed by a plain, unitalicized `Ed` — angle
brackets gone, but the name kept as the label.

Owner is <owner ref="user-42">Ed</owner> today, and the review is due
<due-date>Friday</due-date>. Both pairs above should render as emphasized
labels — `owner:` and `due-date:` — each followed by its plain value, Ed and
Friday, with the `ref` attribute appearing nowhere on the page. Unlike the
whole-line heading conversion in Sections A and B, this rule never reshapes
a name: `due-date` stays exactly as written, so you should see `due-date:`
and never a spaced, capitalized rendering of that name.

These two stay literal on purpose: an empty pair, `<a></a>`, has no value to
emphasize, and a mismatched pair, `<a>value</b>`, never finds a matching
close tag. Both should still show their angle brackets exactly as written
wherever they appear on the page.

#### More field shapes — names the rule accepts, and one it rejects

A real plan doc carries more metadata than a single name and a date, and the
rule is still generic over the name: whatever shape the name takes, it
survives as the label, reproduced verbatim, alongside its value. Each field
below should render as a bullet holding an emphasized name label followed by
its plain value:

- <review_status>Approved</review_status>
- <effortEstimate>3 days</effortEstimate>
- <meta.labels>tui, fixture</meta.labels>
- <gsd:milestone>v1.0</gsd:milestone>
- <label2>needs-docs</label2>

Those five names cover every separator and character class a name may use
beyond the two plain ones above them: an underscore, a run-together capital,
a period, a colon, and a trailing digit. All five should render as five
labels followed by their plain values — `review_status:` Approved,
`effortEstimate:` 3 days, `meta.labels:` tui, fixture, `gsd:milestone:`
v1.0, and `label2:` needs-docs. The colon-separated name is worth a second
look: the rule appends its own trailing colon without inspecting what the
name already contains, so the label renders bearing two colons —
`gsd:milestone:` — one from the name and one added by the rule.

<assignee team="platform" role="reviewer">Dana</assignee>

Attribute stripping is not limited to the single attribute demonstrated
earlier: the field above carries two of them, both discarded, and should
still render as an italic `assignee:` label followed by a plain `Dana`.

Status is <status>In review</status> and priority is <priority level="p1">High</priority> today.

That sentence carries two pairs rather than one, so the scan should replace
both on the same line — `status:` and `priority:` as labels, with `In
review` and `High` as plain values in the flow of the sentence, and no
angle bracket behind either.

A value is trimmed before it follows its label: <reviewer>   Priya   </reviewer>
sits padded with spaces inside its tags, and should still render as an
italic `reviewer:` then exactly one space then a tight `Priya`, regardless
of the padding in the source.

One last pair stays literal, for a subtler reason than the empty and
mismatched pairs above: `<owner>Ed</Owner>` closes with a name differing
from the opening one only in the case of its first letter. Matching is
case-sensitive, so these two never pair up, and it should keep its angle
brackets exactly as written.

That is the full appendix: Section A for depth, attribute stripping, and the
self-closing case; Section B for the six-level cap; Section C for the fenced
contrast that proves all three rules are scoped, not global; Section D for
comment removal; and Section E for same-line inline pairs becoming an
emphasized name label followed by the plain value.
